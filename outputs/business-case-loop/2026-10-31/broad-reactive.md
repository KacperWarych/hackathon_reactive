# Broader reactive-use-case challenge — 31 October 2026

## Finding

Do not lock the project into sales. The reusable capability is **revising a sourced conclusion when its supporting facts, constraints, or commitments change**, while preserving what was believed when. Sales objections are one example, not necessarily the best market. Two non-sales experiments merit equal priority: engineering decision invalidation and technical-support case continuity. Both resemble the implemented investigations workflow without requiring campaign aggregation.

Persistent *application state* is useful across these cases. Persistent *model conversation memory* is not automatically required. An event log, structured state and stateless recomputation can reproduce most candidate workflows. Reactor must earn its role in a controlled comparison. No external source reviewed here establishes demand for this particular product.

## Build from temporal primitives

| Primitive | Minimum correct behavior | Simple baseline | When language reasoning adds something |
|---|---|---|---|
| Contradiction/retraction | Keep conflicting claims, authority and scope; invalidate only conclusions relying on the affected claim | Source-ID withdrawal and dependency edges | Recognizing that differently phrased claims conflict, or that a correction changes only one conclusion |
| Dependency invalidation | Mark downstream decisions for review when a prerequisite becomes false | Explicit graph traversal | Inferring an unstated assumption from discussion; explaining impact without inventing dependency |
| Long-lived commitment | Distinguish proposed, conditional, accepted, completed, cancelled and unknown | Owner + due date + status rules | Extracting conditional commitment and detecting later renegotiation across messages |
| Changing constraint | Re-evaluate selected option against the current requirement set | Structured field comparison/filter | Interpreting an ambiguous requirement and whether it supersedes an older one |
| Evidence confidence | Separate observation, interpretation, authority, corroboration and unresolved disagreement | Source quality/status tags | Explaining exactly why confidence should change; no unsupported numerical probability |
| Temporal boundary | Answer both “what was known then?” and “what is believed now?” | Event time + recorded-at time + immutable versions | Reconciling late-arriving/backdated evidence and revisions without leaking future information |

The last row reveals a real implementation gap: a conversation date filter alone does not establish when the system first knew a fact. Historical report snapshots help, but bitemporal queries need explicit ingestion/knowledge time and semantics. Do not imply full bitemporal correctness from “Answer as of.”

## Eight diverse workflows and mechanism choice

These are candidate jobs and scenarios, not validated buyers or claimed implemented capabilities.

| Workflow / user / concrete decision | Trigger → valuable update | Mechanism most likely sufficient | Fit and important counterargument |
|---|---|---|---|
| Engineering decision review / tech lead / keep or reopen an architecture choice | New measurement contradicts an accepted latency assumption → identify impacted decision and request the one missing check | Rules for measured thresholds + stateless reasoning over decision/evidence; stateful memory only if long negotiation/reference handling improves | Strong report/version/citation reuse; competes with ordinary ADR review and issue links; missing dependency schema |
| Technical-support case handoff / support engineer / next diagnostic step | Customer reports partial fix or regression after workaround → preserve unresolved symptom, avoid repeating failed troubleshooting | Case-state ledger + stateless evidence synthesis; memory potentially helps long diagnostic exchanges | Strong concern/change/quote reuse; product differentiation is semantic scope, not reopening ticket |
| Research evidence maintenance / analyst / retain, qualify or withdraw a report claim | Source corrected/retracted → affected claims and dependent recommendations need review | DOI/source rules + claim dependency graph + stateless impact analysis | Excellent retraction/citation story; no existing paper ingestion or claim graph; status monitoring already exists |
| Client delivery commitment tracking / agency project manager / renegotiate deadline or escalate missing input | Client changes approval criteria after conditional delivery commitment → flag threatened deliverable with original condition | Due-date/dependency rules + language extraction; memory optional | Existing goals/concerns map; customer authority, owner and completion schema absent; cannot assume silence means approval |
| Software vendor selection / operations lead / retain or reopen shortlist | New integration/security requirement makes preferred option ineligible → revise comparison and explain why | Constraint table and deterministic filtering + stateless explanation | Concrete changing-decision demo; episodic use weakens recurring need; stale vendor data is main risk |
| Incident investigation continuity / on-call engineer / next test during handoff | New logs contradict leading hypothesis → demote hypothesis, preserve rejected tests and open questions | Event correlation/rules + stateless causal synthesis; long-memory benefit needs testing | Strong narrative fit but large noisy ingestion, strict latency and observability integrations make near-term reuse weaker |
| Employee/customer onboarding dependencies / coordinator / which task can start | Access granted but prerequisite training incomplete → keep only affected steps blocked | Explicit dependency graph and status rules | Real temporal task but AI mostly unnecessary unless requirements exist only in prose; poor Reactor differentiation |
| Personal plan with changing constraints / individual / keep a selected purchase/travel plan | Budget/date/accessibility preference changes → reopen affected choice and retain unaffected preferences | Structured preference/constraint memory + stateless recompute | Closest original dataset framing; weak buyer, low urgency, hard external factual freshness; existing dataset can test recall not demand |

Existing products supply a demanding baseline: Jira documents explicit blocking links and automation across related work items; GitHub can dismiss stale approvals after changes; Zendesk lets requester replies reopen solved tickets. A solution that only repeats these mechanics has little demonstrated differentiation. [Jira dependencies](https://support.atlassian.com/jira-software-cloud/docs/create-or-remove-dependencies-on-your-timeline/), [Jira related-item automation](https://support.atlassian.com/cloud-automation/docs/branch-automation-rules-to-perform-actions-on-related-issues/), [GitHub stale-review behavior](https://github.blog/changelog/2023-06-06-security-enhancements-to-required-approvals-on-pull-requests/), [Zendesk ticket updates](https://support.zendesk.com/hc/en-us/articles/4408832151834-Updating-and-solving-tickets).

Research status alerts are also an existing capability: Crossmark exposes corrections/retractions/updates, and Crossref provides Retraction Watch data through its API or dataset. The proposed value would be propagating a source change into a user's own claims, not merely announcing the retraction. These services do not establish that every publication change is covered. [Crossmark](https://www.crossref.org/services/crossmark/), [Retraction Watch data](https://www.crossref.org/documentation/retrieve-metadata/retraction-watch/).

## Deep dive 1 — engineering decision invalidation

**Job:** Before shipping or continuing implementation, tell a tech lead which prior decisions need review because a material assumption changed. Output a bounded review card: prior decision, dependency/assumption, new source, consequence, still-valid parts and next verification. Do not automatically reverse the decision or open issues.

**Temporal scenario, grounded in this project:** The actual evaluation report says hybrid reranking and full expansion tied on tuning packed evidence coverage while mean retrieval time was 9.385 versus 25.255 seconds. It selected reranking. This is concrete available evidence; it is not a randomized latency comparison or proof about all future datasets. A controlled demo can explicitly introduce a hypothetical prior ADR: “Use expansion by default because it adds evidence coverage, with a sub-15-second retrieval target.” When the real report arrives, the system should flag the coverage assumption as unsupported on this tuning set and the measured expansion time as over the chosen target. It should recommend reviewing the default, not conclude expansion is useless globally. The target and ADR are synthetic fixture facts and must be labelled so.

**Sequence:** (1) Record hypothetical ADR and scope; (2) add existing real evaluation report; (3) add an unrelated formatting note; (4) add a clearly labelled hypothetical stress result showing expansion helps only large histories. Expected behavior: reopen default-selection decision at step 2, no alert at step 3, narrow rather than blanket-reverse recommendation at step 4. Include a reviewer correction retracting an erroneous measurement to test dependent conclusion withdrawal. Do not overwrite original sources to fake a chronology.

**Why this might beat a generic summary:** The deliverable is a specific decision whose justification no longer holds, with an actionable missing test. Users should not have to reread every prior report to find it. The hard operation is mapping a new observation to an old assumption and identifying the correct scope.

**Baselines:** An ADR table with explicit assumptions and threshold rules; a daily changed-document digest; fresh RAG over ADR plus current reports; persistent Reactor investigation. Give all arms the same source documents and task. Structured rules should win obvious numeric thresholds; AI must improve implicit assumption matching without inventing impacts. Existing workflow software makes a simple “linked task changed” alert insufficient.

**Falsification:** Reject the wedge if a manually maintained assumption table is faster with comparable completeness; if alerts mostly restate linked document edits; if fewer than half of reviewers take a concrete review action; or if invented dependency edges create unacceptable work. For an initial 20-event pilot, prespecify 10 consequential changes and 10 benign changes: target at least 9/10 correct affected decisions, at most one false review card, zero silent reversal or fabricated source. Measure human review time as well as detection. Thresholds are provisional, not results.

**Available data:** Actual local `outputs/evaluation-report.md`, README and implementation notes; local saved report versions where accessible. There is no established real ADR acceptance history in the material inspected. Synthetic ADR/control events provide a transparent demo, not customer validation. Public GitHub issues/PRs could later supply real chronological decision threads, but no such corpus has been collected or evaluated here.

**Practical demo and gaps:** Reuse investigation entry/refresh, cited answer and version diff. Present a single decision report and append source notes manually. The current Customer/Seller role model needs honest relabeling or explicit metadata for author/authority; do not imply a test engineer's quote is user approval. A report template alone cannot provide a dependency graph. For a usable product, add typed decision/assumption IDs, source-dependency links, review state and source-change detection. Existing date/history safeguards remain useful but don't prove known-at-time correctness.

**Memory test:** If stateless RAG with the explicit decision ledger performs equally well, keep the ledger and drop the persistent-model-memory claim. Stateful Reactor is worth retaining only if long sequences with implicit references, partial reversals and prior rejected alternatives improve measurably at equivalent evidence access and cost.

## Deep dive 2 — technical-support handoff with partial resolution

**Job:** Give the next engineer a current, sourced issue state and one useful next diagnostic question, without repeating steps already attempted or treating a partial fix as full resolution.

**Controlled temporal scenario:** Monday customer: “Desktop export works; mobile export fails on CSV and PDF.” Support suggests disabling an extension; customer says the extension is already absent. Tuesday support suggests clearing cache. Customer: “CSV works now, PDF still fails.” Wednesday customer: “CSV failed again after signing in on another account.” Expected states: preserve failed prior tests; mark CSV provisionally improved only after customer confirmation; keep PDF unresolved; reopen CSV on regression; do not infer root cause from correlation. A subsequent “Thanks” should not resolve either issue. All dialogue is a labelled synthetic test fixture, not a real ticket.

**Business value hypothesis:** Faster handoffs and fewer repeated or irrelevant troubleshooting requests. The purchaser hypothesis is a support lead with cases spanning several shifts/engineers. Reopen detection alone is weak differentiation because Zendesk already documents requester-triggered reopening. Scope-aware state and a grounded next diagnostic step are the proposed advantage. [Zendesk ticket updates](https://support.zendesk.com/hc/en-us/articles/4408832151834-Updating-and-solving-tickets).

**Baselines:** Native status rules plus a structured symptom checklist; a manual handoff note; a fresh thread summarizer; fresh RAG over full accessible ticket; persistent Reactor investigation. Avoid giving persistent Reactor more source context than its competitor. Evaluate both small complete threads and longer ones where evidence packing omits earlier failed steps.

**Falsification:** Stop if a two-column symptoms/tests checklist produces the same next step faster; if output confuses agent suggestions with attempted actions; if current evidence packing loses the original symptom decomposition; or if users still reread the full thread to trust the summary. Initial pilot target: correct state on at least 18/20 symptom-event transitions, no false full resolution, and at least 30% median handoff preparation-time reduction versus manual notes without lower expert-rated quality. Evaluate “thanks”, negation, hypothetical tests, partial success, recurrence and multilingual confirmations separately. Small pilots are screening, not population accuracy claims.

**Available data:** The existing app has user/assistant conversations and goals/concerns/changes/resolutions, but the inspected Salesgen corpus is synthetic sales data, not a support benchmark. No real support tickets were acquired. The demo can use controlled fixtures; validation requires consented/de-identified multi-turn cases or an appropriately licensed public support corpus, with a domain reviewer. Public GitHub issues might be a starting source but differ from private customer support and need separate source selection and privacy review.

**Practical demo and gaps:** Reuse one investigation, dated entries, evidence viewer and previous-version diff. Keep each symptom's state in a manually reviewed report rather than pretend a structured symptom ledger exists. Existing resolution validation requires matching user quotes and English cue patterns; it neither validates semantic scope nor reliably handles Polish confirmations. Today it might reject “CSV works now” unless exact cues match, and may still accept an overbroad interpretation if the quote passes. Add semantic evaluation before promoting resolution claims; app changes are outside this research task.

**Memory test:** Persistent memory may help preserve rejected diagnostic branches and references such as “the second workaround.” A persisted structured test ledger plus stateless generation may do this more safely. Compare full-history freshness and source-cited recovery after switching investigations, because the current API can reset/reconstruct history.

## Challenge to the sales blocker brief

### Separate the reactive winner from the business winner

**Strongest reactivity experiment: semantic decision invalidation.** It directly tests whether a changed source should invalidate only some dependent conclusions, including retractions and scope changes. This is stronger than a latest-message summary. It is a provisional technical winner, not a market winner. Explicit dependency edges and numeric thresholds belong to a rule engine; the unresolved AI proposition is discovering justified implicit dependencies from prose while rejecting merely related text.

**Best locally grounded demo: engineering decision invalidation.** We have a real evaluation report with meaningful tradeoffs. We do not have evidence of accessible engineering buyers, buying intent or real ADR lifecycle data. Local document availability is a demonstration advantage only. Atlassian already documents Jira Delivery Agent monitoring stale/blocked/slipping work with recurring automation, so a generic engineering status copilot would face a substantial incumbent. A narrower assumption-evidence invalidation advantage must be measured rather than inferred from a documentation feature gap. [Jira Delivery Agent](https://support.atlassian.com/rovo/docs/work-with-jira-delivery-agent/).

**Business winner: unresolved.** The workflow researcher's fixed-fee agency scope-change triage is a plausible first discovery candidate if the user can access real project briefs, accepted changes and decision-makers. Access has not been established. Its commercial hypothesis is earlier recognition of work beyond an agreed scope; its minimum baseline is a scope checklist plus change log. It loses if it only highlights word differences, cannot establish who authorized a change, or lacks the approved baseline. Support handoff remains the second discovery candidate because repeated cases make value easier to observe, but no real ticket access or incremental advantage over existing support copilots is established. Choose the first pilot by reachable users and usable chronological data, not by which concept sounds most reactive.

- Its strongest currently available evidence is synthetic, and “latest reason for refusal” often reduces to latest-record retrieval rather than long-lived reasoning.
- Current ingestion drops structured customer metadata, so its desired scope is not already enforced. A support case or single engineering decision can align more naturally with one investigation/history, though new data import still needs work.
- Seller action quality and actual commercial outcome are difficult to validate in a hackathon. Engineering assumption invalidation has a more directly inspectable expected answer; support has a clearer bounded state transition.
- Price category changes do not prove a seller needs an interruptive alert; a brief on opening the account may suffice. Likewise, most engineering/support cases may need a ready updated report rather than push notifications.
- Existing contextual sales/support tools are strong substitutes. A feature comparison cannot establish incremental user benefit.

Do not replace sales with a new untested favorite. Run three comparable thin slices—sales concern change, engineering assumption invalidation, support partial-resolution/reopening—with equal demo effort and explicit synthetic-data labels. Choose based on correctness, human decision usefulness and total missing infrastructure. A dataset-friendly demo and a viable business are separate findings.
